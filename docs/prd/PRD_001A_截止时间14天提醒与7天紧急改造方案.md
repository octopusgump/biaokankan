# 标看看｜截止时间 14 天提醒与 7 天紧急改造方案

> 状态：待开发｜更新时间：2026-08-21
>
> 关联主文档：[PRD_001_监理招标信息雷达_首版.md](./PRD_001_监理招标信息雷达_首版.md)

## 一、这是什么？

把现有“3 天内截止”升级为两个互斥的处理层级，让投标人员更早准备，同时先处理真正紧急的项目。

| 状态 | 剩余时间 | 页面标签 | 用户动作 |
|---|---:|---|---|
| 紧急 | `0 < 剩余时间 ≤ 7 天` | 红色“7天内紧急” | 立即判断是否跟进 |
| 提醒 | `7 天 < 剩余时间 ≤ 14 天` | 黄色“8–14天提醒” | 提前准备、持续关注 |
| 正常 | `> 14 天` | 默认样式 | 正常浏览 |
| 已截止 | `≤ 0` | 灰色“已截止” | 不再参与提醒统计 |
| 待核验 | 截止时间不可靠 | 灰色“待核验” | 打开原公告核验 |

**“14 天提醒”不包含“7 天紧急”。** 两组互斥，同一个项目不能同时进入两组统计。

**本方案覆盖旧版“3 天内截止、3 天黄色、1 天红色”的全部规定。** 主 PRD 中相关流程、路由、列表规则、汇总字段和验收条款必须同步修改。

## 二、项目边界

本项目只调整投标截止时间的分类、筛选、汇总、排序、页面标签、数据结构和测试。

本版所说的“提醒”和“紧急提醒”只指项目工作台中的入口、数量和颜色标签；不发送企业微信、短信、邮件或浏览器通知，不新增提醒中心、订阅设置、发送记录或用户配置。

本项目不修改公告抓取来源、截止时间提取规则、招标文件获取窗口、项目去重、原公告核验和访问控制。招标文件获取截止时间仍然不能触发投标提醒、紧急或已截止状态。

## 三、成品长什么样？

项目雷达顶部改成四个入口，默认打开“7天内紧急”：

```text
[7天内紧急] [8–14天提醒] [今日新增] [全部项目]
```

项目列表中的截止时间展示：

```text
投标截止
08月25日 09:30
[紧急 · 剩余 2 天]
```

```text
投标截止
09月02日 09:30
[提醒 · 剩余 10 天]
```

页面规则：

- “7天内紧急”只显示 `urgent` 项目；
- “8–14天提醒”只显示 `reminder` 项目；
- 两组分别按投标截止时间从早到晚排列；
- 标签放在截止时间旁，不给整张项目卡铺满红色或黄色；
- 没有项目时分别显示“未来 7 天暂无紧急项目”和“第 8–14 天暂无提醒项目”；
- 截止状态下拉框改为“全部状态、7天内紧急、8–14天提醒、待核验、已截止”。

首页产品预览保留三个指标：

```text
7天内紧急 | 8–14天提醒 | 真实项目
```

## 四、时间状态怎么计算？

所有入口、列表、详情、首页预览和每日汇总必须调用同一个共享分类函数。投标截止时间统一按北京时间解析。

```js
const DAY_MS = 86_400_000;
const URGENT_LIMIT_MS = 7 * DAY_MS;
const REMINDER_LIMIT_MS = 14 * DAY_MS;

remainingTime = bidDeadline - referenceTime;

if (remainingTime <= 0) deadlineState = "expired";
else if (remainingTime <= URGENT_LIMIT_MS) deadlineState = "urgent";
else if (remainingTime <= REMINDER_LIMIT_MS) deadlineState = "reminder";
else deadlineState = "normal";
```

`bidDeadlineStatus` 不是 `confirmed`、截止时间为空或解析失败时，统一返回 `pending`。

边界口径：

| 情形 | 结果 |
|---|---|
| 截止时间等于当前时间 | `expired` |
| 恰好剩余 7 天 | `urgent` |
| 剩余 7 天加 1 毫秒 | `reminder` |
| 恰好剩余 14 天 | `reminder` |
| 剩余 14 天加 1 毫秒 | `normal` |
| `document_required` | `pending` |
| 招标文件获取时间临近或结束 | 不参与投标截止分类 |

## 五、页面与每日汇总的时间基准

项目工作台使用用户查看页面时的北京时间计算，并每分钟刷新一次分类；这只更新页面状态，不重新扫描来源网站。

工作台顶部数量和当前列表必须从同一次页面计算后的项目集合得出，不能再用静态 `summary` 数量驱动标签，否则项目跨过 7 天、14 天或截止点后会出现“顶部数量和列表不一致”。

每日汇总使用扫描完成时间计算，并显示“统计截至 {generatedAt}”。每日汇总是扫描时的数据产物，允许与当天晚些时候的页面实时状态不同；验收每日汇总时，必须以它自己的 `generatedAt` 回放项目状态。

## 六、每日汇总数据

当前汇总改成：

```json
{
  "summaryVersion": 2,
  "date": "2026-08-21",
  "generatedAt": "2026-08-21T08:13:42.511Z",
  "newProjectCount": 48,
  "urgentWithin7DaysCount": 9,
  "reminderFrom8To14DaysCount": 10,
  "urgentProjects": [
    {
      "projectId": 1162132016,
      "name": "信阳市人民检察院办案用房和专业技术用房建设项目",
      "section": "监理标段",
      "bidDeadline": "2026-08-24 09:00"
    }
  ],
  "reminderProjects": [],
  "abnormalSourceCount": 0
}
```

数据规则：

- `urgentWithin7DaysCount` 统计全部 `urgent` 项目；
- `reminderFrom8To14DaysCount` 统计全部 `reminder` 项目；
- `urgentProjects` 和 `reminderProjects` 分别最多保存最早截止的 3 个项目；
- 两组项目分别按投标截止时间升序排列；
- 当前汇总停止写入 `expiringWithin3DaysCount` 和 `earliestProjects`；
- 汇总计算与 `generatedAt` 必须使用同一个扫描完成时刻，不能一个用扫描开始时间、一个写扫描完成时间。

## 七、快照版本与历史数据

新数据结构版本：

```text
schemaVersion: 4
storage.contractVersion: 4
summary.summaryVersion: 2
```

历史 `summaries` 中的 3 天统计无法准确反推过去的 7 天和 14 天数据，因为旧汇总没有保存当时完整的项目集合。

旧历史记录继续只读保留，并标记为 `summaryVersion: 1`；不伪造历史 7/14 天数量。后续企业微信发送器只能读取 `summaryVersion: 2`。当前 `summary` 只写新结构。

为避免发布期间新页面读到旧快照，第一方页面不得依赖汇总字段生成筛选列表；页面直接从项目的 `bidDeadline` 和 `bidDeadlineStatus` 计算状态。

## 九、当前数据影响

以 `public/data/radar.json` 在 `2026-08-21 16:13` 的快照计算：

| 口径 | 项目数 |
|---|---:|
| 现有 3 天内截止 | 4 |

## 十一、验收清单

1. 默认打开“7天内紧急”，四个入口依次为“7天内紧急、8–14天提醒、今日新增、全部项目”；
2. 恰好剩余 7 天的项目进入紧急，剩余 7 天加 1 毫秒的项目进入提醒；
3. 恰好剩余 14 天的项目进入提醒，剩余 14 天加 1 毫秒的项目进入正常；
4. 同一个项目不能同时进入紧急和提醒；
5. 已截止、待核验和 `document_required` 项目不进入紧急或提醒；
6. 招标文件获取窗口不触发紧急、提醒或投标已截止状态；
7. 两个提醒列表分别按投标截止时间从早到晚排列；
8. 工作台顶部数量与当前筛选结果始终一致；
9. 每日汇总以自己的 `generatedAt` 回放时，数量与项目分类一致；
10. 当前汇总包含两个新数量字段，不再包含 `expiringWithin3DaysCount`；
11. 新快照标记 `schemaVersion: 4`，旧历史汇总仍可读取且不会被伪装成新口径；
12. 用户设备不在中国时区时，截止分类和排序仍按北京时间正确计算；
13. 手机端四个入口呈 2×2，不横向溢出，项目卡标签不遮挡截止时间；
14. 页面不会发送企业微信、短信、邮件或浏览器通知；
15. 爬虫测试、应用构建、GitHub Pages 路由测试和大陆版构建全部通过。
